1 · System picture

A Linux host talks UART32 to a Lattice MachXO3D-9400 FPGA. The FPGA drives two H-bridge motor channels and hosts the ADC, DAC, and temperature peripherals.

Two motor channels. Each channel has its own sequence RAM holding an ON table (open) and an OFF table (close). A trigger plays the table: for each entry, the given H-bridge state and PWM power are held for N PWM periods. The trigger comes from software (0x2007) or from the external AFBR/OCPL inputs.
Measurement. When a sequence starts, the FPGA streams the ADC channels of that bridge into the capture buffer. Afterwards the host reads the buffer back with --get_adc_buff. The SW32 CPU publishes the Pt100 readings in shared memory.

3 · The UART32 protocol

The host is the master and the FPGA's bus is memory-mapped. There is no ACK, no CRC, and no status byte: a write is just bytes out, and a read sends a header and then reads exactly n × word-size bytes.

  • Length is 11 bits, so one burst carries 1–2048 words. psize > 8 forces full=1, and every caller here passes full=1.
  • An address selects a word, so consecutive registers are +1. With ainc=1 the address increments per word.
  • The host writes and reads in 1024-byte chunks. uart::ReadBuffer calls read() once per byte with a 100 ms VTIME.
  • Each single-register access is a full USB round trip, typically around 1 ms for USB-serial (not measured here; read_temps.sh --time measures it). Polling loops pay that on every iteration.
Robustness gap: return codes only report bad arguments. A timeout, an absent board, or a desynchronised stream is never reported, and reads return whatever is in the buffer. Nothing is thread-safe. A NOMAD driver needs a mutex around every packet, short-read detection, and SendBreak/reopen recovery.

Sequence RAM layout and range registers

Each channel has a 2048-entry RAM (log2 = 11, reported in H_STAT bits 7..4). The C code divides it into two fixed halves. The range registers give the start address inside that channel's RAM (11 bits, 0..2047) and length−1 (11 bits, in bits 26..16).

Dropped triggers: what they are and when they happen

Each channel has its own sequencer state machine, hbr_sm in SRC/SHUTTER/hbr_sm.vhd. An ON or OFF trigger reaches it as a pulse one FPGA clock long (about 30 ns). The pulse comes from one of two places:

  • Software: a write to 0x2007 (hbr --start). hbr_dec_cnf.vhd turns bit 0/1 into start_on and bit 2/3 into start_off for exactly one clock.
  • Hardware inputs AFBR and OCPL, if enabled. After a glitch filter a few clocks long and the optional inversion (filt_long), a rising edge becomes ON and a falling edge becomes OFF (hbr_gen.vhd:346-347).

The state machine only looks at ctrl_on/ctrl_off while it is in sm_idle, and only during that one clock. The trigger is not latched or queued, and no error bit is set. If the machine is not ready in that clock, the trigger is simply lost.

stateDiagram-v2
  direction LR
  [*] --> idle
  idle --> seq_start: ON pulse and len_on ≠ 0
  idle --> seq_start: OFF pulse and len_off ≠ 0
  idle --> man_start: single-shot write (0x2004/5)
  seq_start --> seq_read: 1 clk
  seq_read --> seq_next: latch entry (state, dur, power)
  seq_next --> seq_next: each PWM tick while count ≠ 0
  seq_next --> seq_read: count = 0, more entries
  seq_next --> idle: count = 0, last entry
  man_start --> idle: after dur PWM periods
  idle --> idle: busy = 0 · the ONLY state that accepts triggers
  note right of seq_next
    busy = 1 in every state except idle.
    Any ON or OFF pulse that arrives here is lost.
  end note

An sm_reset (bits 4/5 of 0x2007) forces any state back to idle immediately and switches the outputs to Hi-Z.

How long is the sequencer busy?

Busy time ≈ Σ(duration field + 1) over all table entries, times the PWM period, plus 2 clocks. With 25.6 kHz PWM, one period is 39 µs, so the current open.dat and close.dat (411 ms profiles) keep the channel busy for about 411 ms. The busy window is the full length of the waveform file, not just the "move" part.

After the last entry the machine goes back to idle (busy = 0), even when preserve last is on. So holding current does not block the next trigger. While idle with preserve-last on, the held power is capped at MAX_IDLE_POWER_CODE = 64/255 (25 %).

Every way a trigger can be lost

CauseWhen it happens in practiceSymptomAvoid / detect
Channel busy with a sequence A new start within ~411 ms (the table length) of the previous one. Most likely with fast open→close cycling, an operator double-click, or a controller that retries too early. The second move never happens. The first move completes normally. Wait for busy = 0 (0x2002 bit 2 for ch0, bit 3 for ch1) before triggering.
Channel busy with a single shot --single was issued less than dur PWM periods before the start. Same as above. Same busy check.
External pulse shorter than the table AFBR/OCPL pulse width less than the ON table (the OFF edge is lost), or a low gap less than the OFF table (the re-open is lost). Typical when the NIM/timing signal is a short gate rather than a level. The mechanism stays open while the input is low, or the reverse. The two go out of sync until the next edge in the right direction. Keep input pulses and gaps longer than the table, or shorten the tables. Compare 0x2002 bits 8/9 (filtered input level) with the actual position.
Spurious edge on an enabled input initialize_fpga.sh enables both AFBR and OCPL on both channels. A floating, noisy, or unused input can produce an edge that starts a sequence, and the real trigger that follows is then lost to "busy". Unexpected moves, then lost commands. Enable only the inputs that are actually wired (--ctrl_in_afbr/ocpl ch 0 0 for the rest).
Table range disabled (length field = 0) (1) After power-up or make refresh every range resets to 0, so all triggers are ignored until a table is loaded. (2) The field stores length − 1, so a 1-entry table is written as 0 and disabled. compress_power_profile produces a single entry for any constant waveform up to 256 PWM periods (10 ms at 25.6 kHz). Nothing moves, and no error is reported. --hbr_rep shows "disabled". Re-run bring-up and table loads after any refresh. Reject tables with fewer than 2 entries in the driver.
ON and OFF in the same clock Software: the decoder gives ON priority, so OFF is lost (hbr_dec_cnf.vhd:217). Hardware: an AFBR rising edge and an OCPL falling edge in the same clock, where OFF wins in hbr_sm. One direction ignored. Never set both bits. Don't drive AFBR and OCPL from different sources at the same time.
Reset in the same write A write to 0x2007 with the channel's reset bit (4/5) set suppresses that channel's start bit in the same write. Start ignored. Reset and start in two separate writes (the scripts already do this).
MODE2 = 0 The state machine is held in reset while MODE2 = 0 (hbr_sm.vhd:124). This build forces MODE2 = 1 (MODE2_PROG_FIX), so it only matters if that constant changes. Nothing ever runs. —
The current workaround has a cost. The test scripts run --sm_reset 3 before every --start (close_then_open_v2.sh). That guarantees the trigger lands, but if a move is still running it aborts it mid-stroke: the outputs go Hi-Z and power drops to 0 at once, and the new table then starts from wherever the mechanism happens to be. It also hides the fact that the previous move had not finished.
Suggested handling in the NOMAD driver:
  1. Before a move, read 0x2002. If the channel's busy bit is 1, either wait for it to clear or report "busy". Use sm_reset only as a deliberate stop command.
  2. Write the start and read 0x2002 straight away. Busy = 1 confirms the trigger was accepted. A 411 ms table is still running about 1 ms later, so this check is reliable. Tables shorter than the ~1 ms bus round trip would need 0x200C (sequence status) instead.
  3. Poll until busy = 0. That marks "move finished", which is a real status to return to NOMAD instead of an unconditional 0 from hbr_seq_start.
  4. Refuse to load tables with fewer than 2 entries, and after any FPGA refresh re-run bring-up and the table loads.
Source of this analysis. The trigger and busy behaviour described here comes from the VHDL in ../SRC/SHUTTER. That copy is older than the flashed design: it still has the H-bridge block at 0x1000, 1024-entry RAMs, and no ADC-store bits in 0x2007. The address map on this page therefore follows the C headers, which match the flashed design (2048 entries per channel, block at 0x2000). The sequencer and trigger logic is assumed unchanged. The VHDL line numbers quoted above refer to that older copy.
