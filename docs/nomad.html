0 · Short answers

Based on reading driver_testing/nomad-modules: drivers/utilities/rs232port, faulhaber/chopperfaulhaber, ill/fermichopper, ill/choppers_ill, arduino/arduinocoils, controllers/common/{chopper, chopper2, state/stateio, global}, and the GUI XML conventions. NOMAD core (Driver.h, Controller.h) and the Java client are not in this repo, so framework signatures marked confirm are inferred from how modules call them.

Can the FPGA settings go in a "Hardware" tab?

Yes, but on the driver, not on the global controller. In this codebase, the hardware view is built per driver. Each driver ships gui/<type>Plugin.xml with an <image key="HARDWARE_…"/> and a <settings view="…View.xml"/>. That settings panel is where device-level configuration lives: the serial port (RS232PortView.xml), board parameters (ttlView.xml), and so on.

The controllers/common/global module is unrelated. It only holds proposal_change, sample_selector, type_of_measure, and AverageProperties, and it has no hardware settings or driver links.

So the FPGA settings become SAVE properties on the heidelbergchopper driver, edited in its settings view. A registerRefresher writes each change to the FPGA immediately, and INIT re-sends all of them, because an FPGA refresh wipes every register. Things a user changes during an experiment (open/close, chop) belong on a controller, where they are scannable and scriptable.

Communications (decided: option 3). The driver opens the serial port itself through PosixLink, a ~150-line serial class we own (exact-length reads, complete writes, exceptions, 4 Mbit/s, low latency), the way sp15000 opens its own port. uart32's base class uart becomes a thin forwarder to it, so uart32, C_hbr, and the other classes compile unchanged, and the same code runs on the bench (n219ctl) and in NOMAD. NOMAD's rs232port isn't used for data; it doesn't work as it is (§3.6). The port name and speed are the driver::RS232 mixin's saved properties port_device_name and speed.
Controllers. Don't write a new open/close controller. The stock stateio::ShutterController (type shutter) drives any driver that implements stateio::StateIOCommon. It supports masks, so two shutter controllers (mask 0x3 for ch0, 0xC for ch1) can share one board driver, and you get GUI, scan, and sequencer support for free. Chop and ADC capture are driver commands. A small custom controller is only worth adding later if chop needs repetition or timing logic.

class Sp15000Driver : public driver::RS232 {          // transport mixin only — no family interface (see note below)
    friend class RealSp15000Driver;                   // backends reach into the driver's properties
    friend class PerfectSp15000Driver;
public:
    static const std::string TYPE;                    // "sp15000" — the GUI type string

    Property<int32>   active, serialNb, nbChannels, nbSamples;   // one value each
    Property<float64> samplingFreq;
    DynamicProperty<int32>          channelStatus, A1, O1, A2, O2;   // one value PER CHANNEL, resized at runtime
    DynamicProperty<float64>        lengthValue, lengthError;
    DynamicArrayProperty<float64>   xData, yData;                     // a whole array per channel (the trace)

    static const inline std::string MEASURE_LENGTH_COMMAND = "measure_length";   // custom commands are just strings
    static const inline std::string SIGNAL_QUALITY_COMMAND = "signal_quality";

    virtual void execute(const std::string& aCommand);
private:
    void refreshNbChannelsProperty(int32 v);
    enum class State { NONE, BLOCK_READ, LENGTH_READ, QUALITY_READ };   // which long operation is in flight
    State m_state;
};

2 · execute(): one door for every command

void Sp15000Driver::execute(const std::string& aCommand) {
    if (aCommand != STOP && aCommand != STATUS && aCommand != READ)
        sendProgressEvent(PROGRESSION_UNKNOWNSTATE_DEVICE_CONTAINER);       // "something is running"

    Sp15000State* currentState = dynamic_cast<Sp15000State*>(getCurrentState());   // Real or Perfect

    if      (aCommand == driver::INIT_COMMAND)   { m_state = State::NONE;         currentState->init(); }
    else if (aCommand == driver::START_COMMAND)  { startActivated = true;
                                                   m_state = State::BLOCK_READ;   currentState->start(); }
    else if (aCommand == MEASURE_LENGTH_COMMAND) { startActivated = true;
                                                   m_state = State::LENGTH_READ;  currentState->start(); }
    else if (aCommand == SIGNAL_QUALITY_COMMAND) { startActivated = true;
                                                   m_state = State::QUALITY_READ; currentState->start(); }
    else if (aCommand == driver::READ_COMMAND)   { currentState->read(); }
    else if (aCommand == driver::STATUS_COMMAND) { currentState->readStatus(); }
    else if (aCommand == driver::STOP_COMMAND)   { startActivated = false;        currentState->stop(); }
}

Note the shape: commands take no arguments. Three different commands all call start(), and m_state records which one, so the backend knows what to do and what to finish later. That is exactly the pattern our START (open/close) needs while a 411 ms move runs.

    if (IfmValueCount(handle) >= owner()->nbSamples()) {   // ← completion condition

}

    if (v & IFM_STATUS_LASER_STABLE)       s |= LASER_STABLE;  …

}

No threads, no sleeping inside execute(). The driver just says "not finished yet" until the condition holds. Our move does the same, with "is the channel still busy?" (register 0x2002) in place of "enough samples?".

Why one driver for both channels rather than one per channel: both channels share one serial link, one set of chip-wide registers (PWM frequency, decay, TOFF, SLEEP_n live in one HBR_CONF), one ADC pair, and one DAC. One driver owning the port avoids two processes or threads fighting over it, and there is no evidence in this repo of leaf drivers nesting under a leaf. The StateIO mask mechanism was designed for multi-channel I/O boards (arduino_coils, men/m24, ill_A7/*) and gives per-channel controllers on a single driver.

3 · Communications layer

Decision: option 3. The driver opens the serial port itself, through a small serial class we own (PosixLink), the way sios::Sp15000Driver opens /dev/ttyUSB… for its vendor library. NOMAD's rs232port is not used for data. The existing uart32 protocol code sits on top unchanged.

How option 3 fits NOMAD's conventions. Like sp15000, the driver still inherits the driver::RS232 mixin, which gives it the saved properties port_device_name and speed (plus nbbits, parity, bitstop, flowcontrol) and shows them in its settings view. The Real backend reads those two and opens the port. Nothing goes through owner()->DeviceDriver::write/read, so the NOMAD-side binary I/O signatures no longer matter.
confirm on the ILL image RS232::init calls registerParentFunction("rs232"), so check how sp15000 is placed in an instrument configuration and do the same. If our driver has to sit under an RS232Port root, that root's init also opens /dev/ttyACM<leaf-channel−1>. Point it at a different channel number, or at a root that doesn't open anything, so two file descriptors never share the board's port.

3.1 Where the UART code is interfaced

Every hardware access in the project goes through one call chain. The question is which layer to replace. The answer is the lowest one: the uart base class. uart32 uses exactly two of its functions, WriteBuffer (5 call sites: 4 in SendBurst, 1 in RecvBurst) and ReadBuffer (2 call sites). Everything else in uart (SendBreak, WriteSingleByte, BytesSent…) is only used by hbr.cpp's diagnostics or the flash tool.

3.2 The contract the two functions must meet

FunctionHow uart32 calls itWhat the replacement must guarantee
WriteBuffer(p, n) Once per packet for short packets (≤ 8 data bytes) and for all 24-bit bursts, header and data together. For larger 8/16/32-bit bursts it is called several times: header first, then the data in chunks of ≤ 1024 bytes. The return value is ignored Send exactly n bytes in order, or throw. Consecutive calls must go out back-to-back as one stream (the FPGA doesn't care about gaps, only order)
ReadBuffer(p, n) Only inside RecvBurst, right after the header write. n = words × bytes-per-word. The reply has no terminator, length byte, or checksum, so its size is known only from the request. Replies over 1024 bytes are read with several calls (the ADC buffer is 8 transactions and 16 ReadBuffer calls: 15 × 1024 bytes + 1006). The return value is ignored Block until exactly n bytes are in p, or throw on timeout. Never discard input between calls: the second half of a reply may already be waiting in the OS buffer
(transaction) A read is WriteBuffer(header) + one or more ReadBuffer. A big write is several WriteBuffer calls Nothing else may use the port in between. So the lock cannot live inside WriteBuffer/ReadBuffer. Take it around the whole SendBurst/RecvBurst (two small edits in uart32.cpp), or around each board operation in the driver (needed anyway for busy-check → trigger → confirm)
(errors) uart32 and the device classes ignore every return value. 3.4 PosixLink: the serial layer we write

About 150 lines, adapted from today's uart.cpp, with three differences: reads wait for an exact byte count, writes are completed, and every failure throws. It uses only Linux headers, so it compiles unchanged for n219ctl on the bench and inside the NOMAD module.

// n219/PosixLink.h
#include <string>  #include <stdexcept>  #include <cstdint>

struct LinkError : std::runtime_error { using std::runtime_error::runtime_error; };

class PosixLink {
public:
    PosixLink(const std::string& device, int baud, int timeoutMs = 200);   // throws LinkError
    ~PosixLink();                                   // close(fd)
    void write(const uint8_t* p, size_t n);         // all n bytes or throw
    void read (uint8_t* p, size_t n);               // exactly n bytes or throw on timeout
    void flushInput();                              // tcflush(TCIFLUSH)
    void sendBreak();                               // tcsendbreak(fd, 0): UART32 resync
private:
    bool waitFor(short events, int msLeft);         // poll()
    int m_fd = -1;
    int m_timeoutMs;
};

// n219/PosixLink.cpp (essentials)
PosixLink::PosixLink(const std::string& dev, int baud, int timeoutMs) : m_timeoutMs(timeoutMs) {
    m_fd = ::open(dev.c_str(), O_RDWR | O_NOCTTY | O_NONBLOCK);
    if (m_fd < 0) throw LinkError("open " + dev + ": " + strerror(errno));
    termios t{};  tcgetattr(m_fd, &t);
    cfmakeraw(&t);                                  // 8N1 raw: no echo, no CR/LF translation
    t.c_cflag |= CLOCAL | CREAD;
    t.c_cflag &= ~(CSTOPB | CRTSCTS | PARENB);
    t.c_iflag &= ~(IXON | IXOFF | IXANY);
    cfsetspeed(&t, toSpeed(baud));                  // B4000000, B2000000 … ; throw if unknown (no silent 9600!)
    if (tcsetattr(m_fd, TCSANOW, &t) != 0) throw LinkError("tcsetattr");
    serial_struct ss;                               // replaces `setserial … low_latency`
    if (ioctl(m_fd, TIOCGSERIAL, &ss) == 0) { ss.flags |= ASYNC_LOW_LATENCY; ioctl(m_fd, TIOCSSERIAL, &ss); }
    tcflush(m_fd, TCIOFLUSH);
}

void PosixLink::write(const uint8_t* p, size_t n) {
    flushInput();            // in UART32 no reply is pending when the host writes → drops stale bytes, resyncs
    while (n) {
        ssize_t k = ::write(m_fd, p, n);
        if (k > 0) { p += k; n -= k; continue; }
        if (k < 0 && errno != EAGAIN && errno != EINTR) throw LinkError("write: " + std::string(strerror(errno)));
        if (!waitFor(POLLOUT, m_timeoutMs)) throw LinkError("write timeout");
    }
}

void PosixLink::read(uint8_t* p, size_t n) {
    const auto deadline = std::chrono::steady_clock::now() + std::chrono::milliseconds(m_timeoutMs);
    while (n) {
        int left = (int) std::chrono::duration_cast<std::chrono::milliseconds>(deadline - std::chrono::steady_clock::now()).count();
        if (left <= 0 || !waitFor(POLLIN, left))
            throw LinkError("read timeout, " + std::to_string(n) + " bytes missing");
        ssize_t k = ::read(m_fd, p, n);
        if (k > 0) { p += k; n -= k; }
        else if (k == 0 || (errno != EAGAIN && errno != EINTR)) throw LinkError("read failed (device gone?)");
    }
    // NO flush here: the next ReadBuffer call of the same reply reads the bytes already waiting
}

Testing without hardware: PosixLink works on any tty, including a pseudo-terminal. 3.6 For reference: why rs232port (option 1) doesn't work as it is

Kept in case ILL prefers option 2, and so the same checks can be run against the rs232port on the ILL image.

Why rs232port's binary read breaks this, concretely.
  1. It doesn't wait. The port is opened with O_NDELAY (RealRS232PortDriver.cpp:79) and never switched back to blocking, so VMIN=1/VTIME=1 do nothing. The text read(…, terminator) copes by looping with usleep until the terminator arrives. The binary read(uint8*, len) makes a single ::read() straight after the request and returns whatever has arrived, usually nothing yet (the reply is about 1 ms of USB latency away). So even a 1-byte register read would typically return stale buffer contents.
  2. It throws away the rest. It then runs tcflush(TCIFLUSH). For the ADC buffer, RecvBurst reads the 2048-byte reply with two ReadBuffer(1024) calls, and the flush after the first one discards bytes that belong to the second.
  3. Writes aren't checked. On a non-blocking fd a large ::write can be partial. The return value is only logged, so a 1024-byte chunk could go out truncated.
The fix is a binary read that loops until len bytes have arrived or the timeout expires (with poll() or a short sleep), with no flush afterwards, and a write that loops until everything is sent.

4.6 Table management: resident tables instead of reload-per-move

The scripts reload the table before every move. With 2048 entries per channel, the driver can keep open, close, and chop resident and only rewrite a range register (one 4-byte write) when needed:

RAM region (per channel)HoldsRange register
0 … Nopen−1open tableON range points here (permanent). The AFBR/OCPL rising edge also opens
Nopen … +Nclose−1close tableOFF range points here (permanent). The falling edge closes
after thatchop tableFor CHOP only: point the ON range at chop, trigger ON, wait until not busy, restore the ON range

This keeps open = ON = rising edge and close = OFF = falling edge, matching the current scripts and the external trigger inputs. Tables are rebuilt when a waveform file, its resample parameters, or pwm_frequency change (the time step depends on it). The driver rejects tables with fewer than 2 entries (a 1-entry range is disabled in hardware) and tables that don't fit. caution While chop has re-pointed the ON range, an external rising edge would play chop, so disable the inputs during chop or document it.

8 · Open questions

  1. Position feedback. Are the four light-switch inputs (H_STAT b16..19) wired as end-of-travel sensors (two per channel)? If so, actual_value should come from them, giving real position instead of "last completed move".
  2. Chop. A single triggered motion, or repeated with a period? This decides whether a custom controller is needed.
  3. External triggers in production. Will AFBR/OCPL drive the shutter directly? If so, NOMAD's state can drift from the hardware, because the FPGA moves on its own. READ must then derive the state from the input level plus busy, not from software commands.
  4. Placement in the instrument configuration confirm on the ILL image: where does sp15000 sit (which parent)? Do the same, and make sure no RS232Port root also opens the board's tty. Mention the option-3 choice to the NOMAD maintainers at review.
  5. Framework details confirm on the ILL image: the exact DynamicArrayProperty type, registerSpyCommand interval units, and error codes for sendErrorEvent. With option 3, the binary DeviceDriver::write/read signatures no longer matter.
  6. Naming. Keep heidelbergchopper (from the draft), or name it after the board (n219hbridge)?
